# 先给结论

你的底座已经足够强了。接下来最大的风险不是技术不够，而是继续沉迷于“把底座做得更完整”。

辛辣一点说：

> 你现在造出来的是一套很强的工业软件内核，但还不是现场 FA 拿来就能干活的产品。

如果未来半年继续增加领域模块、抽象层、漂亮架构、3D 展示、通用能力，而没有真实协议、设备发现、在线监控、调试、仿真和一键部署，那么 OpenLineOps 最终会变成“架构师很喜欢，现场工程师用不起来”的系统。

你的正确目标不是“彻底消灭开发人员”，而是：

> 在 OpenLineOps 已支持的设备、协议和工艺范围内，现场 FA 不写 C#、Python、前后端、数据库或部署脚本，就能完成建线、联机、调试、发布、投产、追溯和故障恢复。

开发人员不会消失，而是从每个项目现场撤走，集中到上游开发一次性的连接器、设备模板和平台能力。这才是能成立、能规模化的商业模式。

# 一、先把产品边界钉死

## OpenLineOps 应该负责

- 设备连接与语义封装
- 工站及生产路线编排
- 工艺流程和状态机
- 配方、限值和版本管理
- 条码、物料、工单及追溯
- 测试、视觉、烧录、校准等设备协调
- 异常处理、重试、返工、恢复
- 多工站协调和资源互斥
- 发布、部署、回滚、审计
- 在线监控、调试和诊断
- 对接 MES 的工单、状态和结果

## OpenLineOps 不应该负责

- 替代安全 PLC 和硬件急停回路
- 替代 EtherCAT、PROFINET 等实时运动控制
- 替代机器人轨迹和伺服调参
- 做成完整 MES、ERP、SCADA 或 SPC 平台
- 宣称任何陌生设备都能自动接入
- 用 Blockly 重新发明 PLC 编程语言

ISA-95 对企业系统与控制系统边界已经有明确划分，OpenLineOps 最合理的位置是生产执行与设备控制之间的“产线应用层”，不要继续向 ERP/MES 或硬实时控制两端膨胀。[ISA-95 官方说明](https://www.isa.org/standards-and-publications/isa-standards/isa-95-standard)

# 二、选一个必胜的首发场景

不要先做“所有自动化产线”。

建议第一垂直场景锁定为：

> 电子制造行业的 EOL、功能测试、视觉检测、烧录、校准类多工站 PC-Based 产线。

典型参考线：

- 2～4 个工站
- PLC 控制夹具和气缸
- 条码枪或固定式读码器
- 一个视觉设备
- 一个供应商测试或烧录 EXE
- 配方和测试限值
- PASS/FAIL/重试/返工
- MES 下载工单、上传结果
- 完整产品履历和测试证据

这和你现在已有的不可变发布、多工站协调、供应商程序托管、检查点、追溯、恢复能力高度吻合。[现有端到端验证结果](/C:/workspace/SmartMatriX/openlineops/artifacts/production-closure-e2e/20260730050336074-60476/summary.json)

先把这一类线做到现场 FA 一天内完成，再扩其他行业。不要拿第一版去挑战整车总装、连续过程、复杂机器人工作站。

# 三、重新定义产品对象，不要让 FA 面对软件架构

当前的 Project、Application、Topology、System、Capability、Driver、SlotGroup、Flow、Operation、Line、Snapshot、Package 等概念，架构上可能合理，但对 FA 认知负担太大。

现场界面应该只呈现这些对象：

| FA 看到的对象 | 含义 |
|---|---|
| 产线 | 一个完整生产单元 |
| 工站 | 物理站点及计算节点 |
| 设备 | PLC、扫码枪、相机、测试仪、供应商程序 |
| 信号 | 启动、完成、结果、条码、压力、温度等 |
| 动作 | 夹紧、扫码、测试、烧录、复位等 |
| 工艺步骤 | 一段可复用的生产行为 |
| 产品流程 | 工件经过哪些步骤和工站 |
| 配方 | 产品型号对应的参数和限值 |
| 发布版本 | 一套可投产、可回滚的配置 |
| 生产记录 | 工件、过程、结果和证据 |

内部的哈希、绑定 ID、Capability Contract、插件类型、签名包等仍然保留，但只进入“高级模式”。

你的 UI 应该是：

> 添加 PLC → 浏览变量 → 把变量映射为“夹紧完成” → 选择“扫码并验证”模板 → 拖入生产流程 → 仿真 → 发布。

而不是让 FA 自己理解你的领域模型。

# 四、建立真正的零代码组件体系

现有设备会话接口方向正确，包含 Open、Read、Write、Subscribe、Invoke、Health、Diagnostics 等基本能力。[设备会话接口](/C:/workspace/SmartMatriX/openlineops/shared/OpenLineOps.Plugin.Abstractions/IOpenLineOpsDeviceSessionPlugin.cs:1)

但只有接口远远不够。需要构建六层产品对象：

## 1. Connector Package：协议连接器

负责真正的通信代码，例如：

- OPC UA
- Modbus TCP
- TCP/串口
- REST
- MQTT
- 供应商 EXE
- 后续的 EtherNet/IP、S7、相机 SDK、机器人 SDK

## 2. Device Profile：设备档案

描述一个具体设备系列：

- 厂商、型号、固件版本
- 使用哪个连接器
- 地址和凭据配置
- 信号及数据类型
- 支持的动作
- 诊断代码
- 固件兼容范围
- 自带模拟器

## 3. Semantic Mapping：语义映射

把 `DB100.DBX2.1`、`ns=2;s=Station.Ready` 这种原始地址，映射为：

- 设备就绪
- 夹具已锁紧
- 启动测试
- 测试完成
- 故障码
- 安全条件满足

## 4. Capability Template：能力模板

例如：

- `ReadBarcode`
- `ClampPart`
- `RunVisionInspection`
- `ProgramFirmware`
- `ExecuteFunctionalTest`
- `ResetDeviceFault`

流程只依赖能力，不直接依赖某个品牌或地址。

## 5. Operation Template：工艺模板

封装完整行为：

- 前置条件
- 启动动作
- 超时
- 重试
- 取消
- 结果判定
- 追溯字段
- 报警
- 恢复策略

例如“扫码并校验”不是一个 Blockly 方块，而是一套经过验证、带诊断和异常路径的工业组件。

## 6. Commissioning Record：调试记录

保存：

- 设备身份和固件
- 实际连接参数
- 已发现信号
- 信号映射
- 通信测试结果
- 手动动作测试
- 调试时间和人员
- 验证证据

真正的低代码不是“少写几行代码”，而是把行业经验封装进这些组件里。

# 五、现场 FA 的黄金工作流

最终产品必须围绕下面这条旅程设计。

## 1. 新建产线

FA 选择行业模板，例如“电子产品双工站 EOL 测试线”。

系统自动创建：

- 推荐工站
- 标准生产路线
- 常用设备槽位
- 默认异常流程
- 基础追溯模型
- 标准报警和恢复策略

## 2. 添加工站

- 自动发现局域网内 Station Agent
- 显示机器名、IP、版本、健康状态
- 一键注册
- 一键证书和密钥配置
- 一键安装或升级 Agent

不能要求 FA 手工配 PostgreSQL、RabbitMQ、证书目录、Windows ACL 或服务账户。当前部署复杂度已经被架构文档承认，这是产品化必须消灭的成本。[部署复杂度说明](/C:/workspace/SmartMatriX/openlineops/docs/adr/0011-coordinate-production-through-station-agents.md:131)

## 3. 添加设备

- 选择设备品牌、型号或通用协议
- 填写 IP、端口、站号、凭据
- 点击“发现”
- 系统浏览变量、方法及状态
- 点击“测试连接”
- 自动生成诊断报告

Ignition 已经把设备浏览、当前值、数据类型、Tag 创建做成了标准体验；OpenLineOps 至少要达到这个基准。[Ignition Tag Browser](https://docs.inductiveautomation.com/docs/8.3/platform/tags/tag-browser) [Ignition 设备变量创建](https://docs.inductiveautomation.com/docs/8.3/platform/tags/creating-tags)

## 4. 映射设备语义

系统推荐映射：

- `Ready → 设备就绪`
- `Busy → 设备执行中`
- `Complete → 执行完成`
- `ResultCode → 结果代码`

FA 可以实时查看值、质量、时间戳和变化趋势。

## 5. 执行调试

- Watch 表
- 单次读取
- 受控写入
- 调用动作
- 重连测试
- 超时测试
- 断线测试
- 设备健康及原始诊断

所有写入必须受工站模式、权限、设备状态和操作策略限制，不能做成无条件“强制变量”。

## 6. 组装产品流程

FA 从模板库拖入：

- 获取工单
- 扫码
- 夹紧
- 视觉检测
- 功能测试
- 判定
- 上传结果
- 放行或返工

默认使用高层工艺模板。只有高级用户才展开底层步骤。

## 7. 配置配方和限值

- 强类型参数
- 单位
- 范围
- 默认值
- 型号继承
- 审核和发布
- 哪个版本用于哪个批次

你现在增加的 Recipe 生命周期、TestPlan、LimitSet、MeasurementResult 方向是对的，但必须垂直打通，不能把 Quality 再扩建成一个独立大平台。

## 8. 离线仿真

每个认证设备档案必须带模拟器：

- 正常完成
- 超时
- 断线
- Bad Quality
- FAIL
- 供应商程序崩溃
- 重启恢复
- 重复消息

没有模拟器的组件，不应被标记为“FA 零代码组件”。

## 9. 干运行和验证

系统输出 FA 能看懂的问题：

- “夹紧步骤缺少松开异常路径”
- “测试完成信号没有超时”
- “型号 A 未设置温度上限”
- “工站 2 没有匹配烧录设备”
- “发布后工站 1 的设备地址会发生变化”

不要只返回 Contract Hash 不匹配或内部异常栈。

## 10. 发布、部署和回滚

- 显示此次发布改了什么
- 显示受影响工站
- 预检查设备、磁盘、版本和连接
- 一键发布
- 灰度到单站
- 验证后全线部署
- 失败自动停止扩散
- 一键回滚上一版

成熟工具普遍提供项目比较、在线调试和部署能力；例如 CODESYS 已包含断点、变量监控和项目比较等工程能力。[CODESYS Development System](https://www.codesys.com/products/engineering/development-system/)

# 六、12～18 个月执行路线

以下按 8～10 人有效团队估算。如果基本靠你一个人，现实周期是 18～24 个月，而且首发协议和行业必须再砍一半。

## 阶段 0：收口与冻结，2～4 周

目标：从“平台开发”切换成“参考产线交付”。

交付物：

- 一份产品宪法：目标用户、支持边界、非目标
- 确定一条双工站参考线
- 列出首发五类设备
- 完整 FA 用户旅程
- 当前操作步骤和时间基线
- 参考线验收用例
- 招募两名真正做现场调试的 FA 参与评审

冻结：

- 新的领域模块
- 3D 功能扩张
- 非试点要求的通用抽象
- 全行业设备兼容口号

验收：

- 所有人能用同一段话解释 v1 做什么、不做什么
- 参考线每个硬件、信号、动作、异常均已明确

## 阶段 1：单工站零代码联机，0～3 个月

重点：

- 冻结 Device Session ABI v1
- 连接器版本和兼容策略
- OPC UA 连接器
- Modbus TCP 连接器
- 通用 TCP/串口扫码器
- 加固供应商 EXE 托管
- 设备连接中心
- Tag/Signal Browser
- Watch、Read、Write、Invoke
- 设备健康和诊断
- 本地模拟器
- 单机安装模式

协议优先级建议：

1. OPC UA
2. Modbus TCP
3. TCP/串口扫码设备
4. 现有供应商 EXE
5. REST/MES 接口

OPC UA 不只是通信协议，它还提供发现、信息模型、安全和设备到企业层的互操作基础，适合作为第一战略连接器。[OPC UA 概述](https://reference.opcfoundation.org/specs/OPC-10000-1/4) [OPC UA Companion Specifications](https://opcfoundation.org/about/opc-technologies/opc-ua/ua-companion-specifications/)

验收门槛：

- FA 不使用终端、JSON、SQL 和源码
- 30 分钟内接入一个标准设备
- 60 分钟内完成第一个受控动作
- 拔网线、重启设备后能自行诊断并恢复

## 阶段 2：双工站建线与复用，3～6 个月

重点：

- 10～15 个标准工艺模板
- 能力匹配和自动绑定
- 产品路线向导
- 配方、限值和审批垂直打通
- 设备模拟器和故障注入
- 复制、粘贴、批量映射
- 项目比较
- Undo/Redo
- 工程资源升级和迁移框架

必须立即修正当前“旧版本直接拒绝、没有迁移”的策略。[当前格式兼容说明](/C:/workspace/SmartMatriX/openlineops/docs/automation-project-workspace.md:212)

工业项目要活五到十年。没有迁移能力，平台升级就等于逼客户重新调线，这是致命问题。

验收门槛：

- 准备好的硬件上，FA 一天内完成双工站首件良品
- 项目自定义源码为 0
- 70% 以上流程来自模板
- 所有标准设备都有模拟器

## 阶段 3：达到现场调试工具水平，6～9 个月

重点：

- 在线步骤时间线
- 信号变化追踪
- 工艺断点
- 有安全约束的单步、跳过和重试
- 当前执行路径高亮
- 慢步骤分析
- 断线、超时、Bad Quality、程序崩溃注入
- 工站更换和配置恢复
- 调试检查表
- 调试证据自动归档
- 错误的可能原因和建议动作

NI TestStand 的竞争力不只是序列编辑，而是开发、调试、部署、并行执行、报告和数据库的完整闭环。[NI TestStand](https://www.ni.com/en/support/downloads/software-products/download.teststand.html/)

验收门槛：

- 给 FA 人为植入 10 个典型故障
- 90% 不需要开发人员介入
- 故障定位中位时间低于 15 分钟
- 连续运行 100 件无丢失追溯、无重复执行

## 阶段 4：生产级运行，9～12 个月

重点：

- OIDC/Active Directory
- 工厂、产线、工站、动作级 RBAC
- 操作原因和变更审计
- 备份和恢复
- 版本差异和回滚演练
- Agent 批量升级
- PostgreSQL/RabbitMQ 高可用部署包
- 断网降级和恢复
- MES 标准适配层
- 生产监控和告警

当前 Engineering、Operator、Safety 三类静态角色只是原型级安全模型，无法支撑真实工厂治理。[现有 API 权限模型](/C:/workspace/SmartMatriX/openlineops/docs/coordinator-api-security.md:46)

验收门槛：

- 两条真实试点线
- 连续运行 30 天
- 完成断网、Agent 重启、数据库恢复、版本回滚演练
- 追溯完整率 100%
- 无法恢复的问题有明确证据包，不依赖开发远程猜测

## 阶段 5：组件生态，12～18 个月

重点：

- Driver SDK
- 驱动一致性测试套件
- 驱动模拟器标准
- 认证等级
- 厂商、型号、固件兼容矩阵
- 组件目录或市场
- LTS 版本和迁移承诺
- 合作伙伴开发手册
- 新协议按客户需求扩展

每个认证连接器必须同时交付：

- 发现
- 配置 Schema
- Read/Write/Subscribe/Invoke
- Quality 和 Timestamp
- 重连
- 健康和诊断
- 模拟器
- HIL 测试
- 示例设备档案
- 固件兼容矩阵
- 升级策略

验收门槛：

- 新产线 80% 以上来自认证组件
- 第二条同类线的工程工作量下降 60% 以上
- 外部合作伙伴能仅凭文档开发并通过一个驱动认证

# 八、安全问题要立刻纠正

你的文档正确说明软件取消不能代替硬件安全系统。[安全边界说明](/C:/workspace/SmartMatriX/openlineops/docs/station-agent-security.md:331)

但 UI 里直接叫“E-STOP”很危险。[当前 E-STOP UI](/C:/workspace/SmartMatriX/openlineops/apps/desktop/src/renderer/operations-workbench.tsx:790)

应立即改成：

> 远程停止请求  
> Remote Safety Stop Request

并明确：

- 不代替硬件急停
- 不代替安全 PLC
- 不保证安全响应时间
- 最终动作必须落到经过风险评估的设备执行器
- 所有远程停止请求必须审计

在没有功能安全认证之前，绝对不要把软件按钮宣传成急停。这不是文案问题，是责任边界问题。

| Studio/桌面工程师 | 2 | 工作流、设备浏览、调试 |
| Runtime/平台工程师 | 2 | 执行、恢复、发布、部署 |

| 解决方案工程师 | 1 | 驻场试点和组件沉淀 |

关键是必须有人每周在真实设备旁边工作。不能全员坐在办公室里凭想象设计 FA 产品。

# 十、衡量成败的指标

北极星指标只有一个：

> Time to First Good Unit：从空项目到首件良品的时间。

配套指标：

| 指标 | v1 目标 |
|---|---:|
| 标准设备接入时间 | ≤30 分钟 |
| 双工站首件时间 | ≤1 个工作日 |
| 参考线项目代码量 | 0 |
| 标准组件覆盖率 | ≥80% |
| 流程模板复用率 | ≥70% |
| FA 独立任务完成率 | ≥90% |
| 典型故障定位中位时间 | ≤15 分钟 |
| 生产追溯完整率 | 100% |
| 故障恢复后重复执行 | 0 |
| 发布和回滚成功率 | ≥99% |
| 第二条同类线工程时间下降 | ≥60% |

不要用代码行数、模块数、插件类型数、测试数量作为产品进展指标。那些只能证明你在开发，不能证明 FA 能交付。

# 十一、未来 30 天的具体工作

按这个顺序，不要打乱：

1. 写出一页产品宪法和明确的非目标。
2. 选定一条双工站参考线。
3. 列出线上所有真实设备、协议、动作和故障。
4. 找两名外部或非核心开发 FA 做基线测试。
5. 记录他们当前每一步花费的时间和遇到的问题。
6. 冻结 Device Session ABI v1。
7. 做 OPC UA 最小连接器。
8. 做第一个设备浏览器和实时 Watch。
9. 做通用 TCP/串口扫码器档案。
10. 做“扫码并校验”第一个完整工艺模板。
11. 做连接器模拟器和 HIL 骨架。
12. 设计单机一键安装模式。
13. 设计工程资源迁移框架。
14. 把 UI 中的 E-STOP 更正为远程停止请求。
15. 建立每周一次 FA 可用性测试。
16. 同时寻找两条真实试点线，不要等产品“完成”才找客户。

30 天结束时不要求完整投产，但必须出现这个闭环：

> FA 新建项目 → 发现 OPC UA 设备 → 浏览变量 → 完成语义映射 → 调用一个动作 → 查看诊断 → 保存调试记录。

# 十二、必须停止做的事情

- 暂停扩展新的大领域模块。
- 暂停非试点需要的 3D 功能。
- 暂停增加更多抽象层和插件种类。
- 不做完整 MES。
- 不做 PLC、机器人或安全系统替代品。
- 不先做 AI Copilot。基础流程都不顺时，AI 只是给混乱加自然语言包装。
- 不把 Blockly 当核心卖点。
- 不追求“连接所有设备”，先认证五类设备。
- 不允许新功能脱离参考线和现场 FA 验收。
- 不再用内置测试 Helper 代替真实硬件证据。

最后一句最直白的判断：

> 你的底座已经过了“还要不要继续做”的阶段，现在进入了“能不能狠下心从架构师切换成工业产品经理”的阶段。

从现在开始，任何一个新需求都只问两个问题：

1. 它是否减少现场 FA 的一个步骤？
2. 它是否让一种真实设备或真实故障不再需要开发介入？

两个答案都是“否”，就不该进入近期版本。
